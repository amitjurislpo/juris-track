Build a complete, production-ready internal web application called **JurisTrack** for **Juris LPO**.

JurisTrack is an employee time-tracking and productive-hours management platform. The primary purpose is to accurately track how much time each employee spends working during the day, how much time they spend on breaks, and calculate their total productive hours. The system must support dynamic team creation, employee management, independent employee timers, break/resume functionality, and manager dashboards.

Do not create a Phase 1 / Phase 2 / Phase 3 implementation. Treat everything below as the complete product requirement and build the application cohesively in one development effort.

## Core Product Concept

Every employee has their own independent work timer.

When an employee starts working, their timer runs continuously and their productive time increases.

When the employee takes a break:

* The productive timer must stop.
* The break period must be recorded.
* The employee can see that they are currently on break.
* When the employee clicks **Back to Work / Resume Work**, the productive timer starts again.
* Productive time must not increase while the employee is on break.
* The employee's timer must be completely independent from every other employee's timer.
* One employee starting, stopping, resuming, or ending their day must never affect another employee's timer.
* The system must calculate productive hours from actual recorded work sessions rather than relying only on a frontend counter.

The application must persist all important time-tracking information in **PostgreSQL**.

## Employee Workday Flow

The primary employee workflow should be extremely simple.

When an employee begins their day:

**Start Work**

The system creates an active work session.

The dashboard should immediately display something similar to:

**Working**

`02:37:14`

with a prominent **Take Break** button.

The timer should continue accurately even if:

* The page is refreshed
* The browser is minimized
* The employee navigates within the application
* The computer remains idle from the frontend perspective

Do not implement the timer as a simple `setInterval` whose value is stored only in React state.

The source of truth must be timestamps stored in PostgreSQL.

Calculate the displayed elapsed time from timestamps so that refreshing the page does not reset the timer.

## Break Workflow

When the employee clicks:

**Take Break**

the current work session should be closed/paused and a break session should begin.

The UI should clearly change to:

**On Break**

`00:18:42`

and show:

**Back to Work**

While the employee is on break:

* Productive hours must not increase.
* Break duration must increase.
* The employee status must be `ON_BREAK`.

When the employee clicks **Back to Work**:

* Close the current break session.
* Create/resume a new work session.
* Employee status becomes `WORKING`.
* Productive time begins increasing again.

An employee may take multiple breaks during one workday.

Every break must be individually recorded.

For example:

Work:
09:00 → 11:15

Break:
11:15 → 11:30

Work:
11:30 → 13:00

Break:
13:00 → 13:45

Work:
13:45 → 18:00

The system should calculate:

Total span:
09:00 → 18:00 = 9 hours

Break:
1 hour

Productive:
8 hours

Do not calculate productive hours merely as "current time minus login time." Use actual work and break intervals.

## End Workday

Provide an obvious:

**End Workday**

button.

When clicked:

* Close the current active work session.
* Mark the employee's workday as completed.
* Calculate final productive hours.
* Calculate final break hours.
* Store the final state.
* Prevent accidental duplicate work sessions for the same day.

If the employee is currently on a break, define sensible behavior and prevent inconsistent records. Prefer requiring the employee to resume work before ending the workday, or clearly handle the break as an ended interval if the product design requires it.

After ending the day, display a summary:

**Today's Summary**

* Workday start
* Workday end
* Total worked span
* Productive hours
* Break hours
* Number of breaks

## Independent Employee Timers

This is a critical requirement.

Every employee's work state must be completely independent.

For example:

Employee A:
WORKING — 05:23:10 productive

Employee B:
ON BREAK — 03:41:22 productive

Employee C:
WORKING — 06:12:05 productive

Employee D:

Changing Employee B's status must never modify Employee A, C, or D.

Never create one global timer for all employees.

Each employee must have their own work-session and break-session records associated with their own employee/user ID.

## Productive Hours Calculation

Productive hours should be calculated from WorkSession records.

For a completed workday:

Productive Time =
sum of all completed work-session durations.

Break Time =
sum of all completed break-session durations.

Total Workday Span =
workday endedAt - workday startedAt.

Do not rely on manually entered productive-hour values.

For an active workday, calculate current productive time using the active work session's `startedAt` and the current server/client time while keeping PostgreSQL timestamps as the source of truth.

Handle timezone consistently.

The organization should have a clearly defined timezone configuration rather than assuming the browser timezone.

## Time Tracking Integrity

This is one of the most important aspects of the platform.

The backend must validate all state transitions.

Use server-side validation and database transactions where necessary.

Handle race conditions so double-clicking buttons does not create duplicate sessions.

## Timer Accuracy

Do not store an incrementing counter such as:

`productiveSeconds = productiveSeconds + 1`

as the authoritative database value.

Store timestamps.

For an active work session:

`productive duration = current time - startedAt`

For completed work sessions:

`productive duration = endedAt - startedAt`

Then aggregate all sessions.

The frontend timer should derive its display from timestamps and periodically synchronize with the server.

Refreshing the browser must not reset the timer.

Opening the same employee account in another browser should show the same underlying work state rather than creating a separate timer.

## Important Product Principle

The system should treat the database timestamps and work/break sessions as the source of truth.

The visible timer is only a representation of the underlying timestamps.

For example, if an employee starts working at 9:00 AM, takes a break at 11:00 AM, returns at 11:30 AM, and ends work at 6:00 PM:

Work session 1:
09:00 → 11:00 = 2 hours

Break:
11:00 → 11:30 = 30 minutes

Work session 2:
11:30 → 18:00 = 6.5 hours

Final productive time:
8.5 hours

Final break time:
30 minutes

This calculation must remain correct after browser refreshes, navigation, reconnection, and manager viewing.
